# DIRS Phase 5A — Optimization Layer Pre-Implementation Validation Plan

## Executive Summary

This document specifies the validation plan, automated test suite architecture, infeasibility handling mechanisms, baseline comparison methodology, weight sensitivity analysis, and performance verification criteria for the Phase 5 Optimization Layer. 

The validation framework guarantees that optimization recommendations generated by DIRS are mathematically sound, physically achievable, policy-compliant, and executable within strict target latency budgets (**Target: $<2.0\text{s}$ wall-clock execution for $N=50$ incidents `[TARGET]`**).

---

## 1. Solver Infeasibility Detection & Relaxation Strategy

In catastrophe scenarios, demand often exceeds available inventory ($\sum d_{i,r} > \sum s_{j,r}$) or road blockages disconnect certain incident nodes. Hard constraint solvers would return `INFEASIBLE` or crash, rendering the system useless during a major crisis.

To prevent solver failure, Phase 5 implements a **Hierarchical Relaxation & Penalty Strategy**:

```
                       ┌───────────────────────────────┐
                       │ Solver Invocation (OR-Tools)  │
                       └───────────────┬───────────────┘
                                       │
                         Status Check  │
                                       ▼
                       ┌───────────────────────────────┐
                       │ Solution Found (FEASIBLE) ?   │
                       └───────┬───────────────┬───────┘
                               │               │
                            YES│             NO│(Infeasible)
                               ▼               ▼
                       ┌──────────────┐ ┌───────────────────────────────┐
                       │ Return Plan  │ │ Activate Hierarchical         │
                       └──────────────┘ │ Relaxation Engine             │
                                        └───────────────┬───────────────┘
                                                        │
                                                        ▼
                                        ┌───────────────────────────────┐
                                        │ 1. Activate Demand Slack      │
                                        │    Variables (xi_ir)          │
                                        │ 2. Allow Unvisited Low-Pri    │
                                        │    Nodes (Drop Penalty)       │
                                        │ 3. Flag Alert to Govt Dashboard│
                                        └───────────────┬───────────────┘
                                                        │
                                                        ▼
                                        ┌───────────────────────────────┐
                                        │ Return Relaxed Feasible Plan  │
                                        └───────────────────────────────┘
```

## 2. Experimental Control: Baseline Algorithms & Input Standardization

All Phase 5 optimization benchmarks will evaluate three decision algorithms against **identical input datasets** (incidents, coordinates, resource stocks, vehicle fleets, shelter capacities, road graph, and priority scores):

1. **BASELINE A (Greedy Proximity / Nearest Feasible Resource)**:
   Dispatches nearest available depot/vehicle with stock to fulfill demand without global route optimization or time-window SLA planning.
2. **BASELINE B (First-Come-First-Served / FCFS Queue Order)**:
   Fulfills incident demands strictly in chronological order of creation timestamp until vehicle capacity or depot stock is exhausted.
3. **OPTIMIZED (Phase 5 Engine)**:
   Phase 5 two-stage multi-objective engine (`NetworkX` graph matrix + `OR-Tools CP-SAT` allocation + `OR-Tools Routing` CVRPTW solver).

## 3. Objective Weight Sensitivity Analysis Plan

To prevent locking arbitrary static weights prior to empirical testing, sub-phase 5K will execute a formal Weight Sensitivity Plan across four candidate configurations:

- **Config 1 (Priority-Heavy)**: $\alpha_1 = 15.0, \alpha_2 = 10.0, \alpha_3 = 1.0, \alpha_4 = 0.1$
- **Config 2 (Balanced)**: $\alpha_1 = 10.0, \alpha_2 = 5.0, \alpha_3 = 1.0, \alpha_4 = 0.2$
- **Config 3 (Distance-Heavy)**: $\alpha_1 = 5.0, \alpha_2 = 2.0, \alpha_3 = 1.0, \alpha_4 = 1.0$
- **Config 4 (Response-Time-Heavy)**: $\alpha_1 = 8.0, \alpha_2 = 12.0, \alpha_3 = 3.0, \alpha_4 = 0.1$

For each configuration, the automated benchmark script will record:
- Total Unmet Demand (%)
- Mean Response Delay (mins)
- Total Travel Distance (km)
- SLA Compliance Rate (%)
- High-Priority Incident Coverage (%)

The final production default weight configuration will be selected based on Pareto efficiency across the test suite and documented with empirical justification.

## 4. Quantitative Verification Test Suite Matrix

When Phase 5 implementation begins, the test suite (`backend/tests/test_optimization.py`) will execute the following automated validation checks:

| Test ID | Test Category | Target Component | Description & Target Acceptance Criteria `[TARGET / REQUIREMENT]` |
| :--- | :--- | :--- | :--- |
| `TEST-OPT-01` | **Capacity Constraint** | Vehicle Routing | Assert total payload assigned to any vehicle $v$ does not exceed $Q_v^{\text{weight}}$ or $Q_v^{\text{vol}}$. |
| `TEST-OPT-02` | **Blockage Non-Traversal** | Graph & Routing | Verify 0 routes contain edges marked as impassable in `RoadBlockage` table. |
| `TEST-OPT-03` | **Inventory Conservation** | Resource Allocation | Assert total allocated resources $\sum y_{j,i,r} \le \text{total available depot stock } s_{j,r}$. |
| `TEST-OPT-04` | **Shelter Capacity Bound** | Shelter Assignment | Assert allocated evacuees $z_{i,k} \le (C_k^{\text{shelter}} - O_k^{\text{shelter}})$. |
| `TEST-OPT-05` | **Infeasibility Resilience**| Solver Slack | Induce artificial demand spike ($d > 500\% \text{ supply}$); assert solver returns partial allocation without error. |
| `TEST-OPT-06` | **Latency Benchmark** | Performance | Target: Assert wall-clock execution time for $N=50$ incidents, $M=10$ depots, $K_v=25$ vehicles is $<2,000\text{ms}$ (`TARGET`). |
| `TEST-OPT-07` | **Priority Sensitivity** | Objective Function | Assert incident with $P_i=95.0$ receives resource allocation before incident with $P_i=25.0$. |
| `TEST-OPT-08` | **HITL Audit Trace** | Governance | Assert approving or modifying an optimization run generates a valid `AuditLog` entry. |

## 5. Performance & Target Latency Metrics

- **Primary Solver**: Google OR-Tools CP-SAT + Routing Library.
- **Max Target Latency**: 2,000 milliseconds total optimization latency for DIRS-50 benchmark (`TARGET`).
- **Target Optimality Gap**: $\le 2.0\%$ gap from theoretical lower bound (`TARGET`).
- **Benchmark Scenario Execution**: 100% of benchmark test cases must complete cleanly without throwing unhandled solver exceptions.
